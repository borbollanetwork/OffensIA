# OffensIA v1.2 — Autonomous Operational Core (Design Specification)

**Date:** 2026-09-23
**Status:** Approved (design phase)
**Supersedes/extends:** `docs/specs/2026-09-22-offensia-design.md`
**Origin:** external review (`melhoria.md`) evaluated and accepted with adjustments.

---

## 1. Purpose

v1.1 is a well-governed MCP gateway over two engines. v1.2 turns OffensIA into an
**autonomous operational orchestrator**: an internal planner drives a disciplined
loop that turns a normalized surface into intelligence-derived hypotheses, runs
**typed** experiments serially, confirms them with **semantic oracles**, records
**canonical findings**, and reasons over an **attack graph** — all still enforced in
code, never by prompt.

The autonomy sits **above** the safety controls and bypasses none of them:
scope (default-deny), typed-job validation, evidence gate, validation, and the
hash-chained ledger remain mandatory on every action.

### The loop
```
state (surface/assumptions/hypotheses/coverage/budget)
  -> planner asks the LLM (Kimi/GLM) for the next typed action
  -> capability registry -> policy -> adapter -> serial executor
  -> semantic oracle (baseline + negative control + reproduction)
  -> structured evidence -> canonical finding -> requires/grants
  -> attack graph -> coverage update -> next (or stop)
```

### Success criteria
- An engagement runs end-to-end autonomously from an objective + authorized scope,
  producing canonical findings backed by semantic oracles and a verifiable ledger.
- No `generic.command` path exists; every action is a validated `ExecutionJob`.
- Exactly one experiment is active at a time; an interrupted run resumes
  deterministically from the last confirmed checkpoint with no lost evidence and no
  blind re-execution.
- A finding is confirmed only through a semantic oracle (not process exit code).
- Confirmed attack paths contain only validated edges.
- Out-of-scope targets are refused per job; lateral-movement jobs pause for human
  confirmation.

### Non-goals (v1.2)
- No parallel/threaded execution (serial only, by design).
- No CTI/CVE ingestion engine, no exploit-sandbox promotion pipeline (later).
- No embeddings-based retrieval (BM25 + section chunking is a separate, later item).
- No deep expansion of web3/iot/wireless/binary domains (product focus: web → API →
  AuthZ → cloud/IAM).

## 2. Subsystems and files

### 2.1 Typed execution jobs — `offensia/core/jobs.py`
Replaces `generic.command`. An `ExecutionJob` is a validated dataclass:

```
job_id, capability, tool_id, argv[], targets[], identity_context,
preconditions[], request_cap, rate, timeout, expected_oracle,
negative_control, cleanup_plan, evidence_contract, risk_class
```

Validation (code-enforced before anything runs):
- every target ∈ scope (normalized); otherwise refuse + ledger deny.
- `tool_id` known; `argv` conforms to that tool's arg allowlist/schema.
- caps (`request_cap`, `rate`, `timeout`) applied.
- `expected_oracle` names a registered oracle; `negative_control` present when the
  oracle requires it.
- **availability guard**: refuse if `risk_class ∈ {dos, availability_impact,
  crash}` or if `tool_id`/`argv` match the disruptive denylist (flood/stress/DoS
  modules, crash-inducing flags).
- **destruction guard**: refuse if the job's declared effect targets a pre-existing
  target-owned resource for delete/overwrite/truncate; only self-created artifacts
  (`origin=offensia` + engagement id, recorded in `evidence_contract`/`cleanup_plan`)
  may be created and later removed.

MCP: `offensia_run_job(job)`; `offensia_exec` is removed.

### 2.2 Serial executor — `offensia/core/executor.py`
- One active job per assessment; persistent lock (`<assessment>/.lock`) blocks a
  second executor.
- `actions.jsonl` append-only, monotonic seq + timestamp, one record per lifecycle
  transition (intent → running → completed/failed/interrupted).
- stdout/stderr streamed to `<assessment>/actions/<seq>.out|err` with periodic flush.
- Atomic checkpoint: write `state.json.tmp`, `fsync`, `rename`.
- Every artifact → SHA-256 + size + origin + action_id + timestamp in the evidence
  store; the LLM context holds only refs/summaries, never the sole copy.
- Resume: a job with intent/running but no terminal event is `interrupted`, never
  assumed complete; before re-running, check idempotency, partial evidence, and
  pending cleanup.
- **Health-aware halt**: probe target availability before a job and after producing
  output; if the target is unreachable/unhealthy, halt the engagement (mark the job
  `interrupted`, do not keep sending) instead of hammering an already-down target.
- **Cleanup owns only self-created artifacts**: cleanup runs only `cleanup_plan`
  steps for resources marked `origin=offensia`; it never touches pre-existing
  target data.

Executor flow: `plan → record intent+preconditions → mark running → run serial →
persist stream incrementally → hash + evidence refs → update coverage/hypotheses/
findings → atomic checkpoint → mark terminal → next`.

### 2.3 Semantic oracle framework — `offensia/core/oracles/`
`base.py` defines:
```
class Oracle:
    name: str
    requires_negative_control: bool
    def evaluate(self, ctx: OracleContext) -> OracleVerdict
```
`OracleContext` carries baseline, candidate, negative-control results (from the
executor) and target/identity. `OracleVerdict` = {reproduced: bool, confidence,
evidence_refs, rationale}. Reproduction requires multiple attempts + perturbation
where applicable.

v1.2 oracles (extensible; "other classes" plug in as new `Oracle` subclasses):
- `HTTPDifferentialOracle` — baseline vs payload vs negative control on responses
  (injection, reflection, boolean/blind); not exit code.
- `AuthorizationOracle` — BOLA/BFLA/IDOR: context A obtains what only B should, with
  a negative control proving the boundary normally holds.
- `FileReadOracle` — canary-file read proving traversal/inclusion before any
  sensitive path.
- `OASTOracle` — controlled out-of-band callback for blind SSRF/RCE/Log4Shell
  (requires an OOB listener; see open items).

Promotion (in `finding.py`) keys on oracle verdicts, not process success.
`EXPLOITABLE` and `CONFIRMED_IMPACT` get **stricter, distinct** requirements from
`VALIDATED` (e.g. demonstrated primitive / impact validation, not just reproduction).

### 2.4 Canonical finding — `offensia/core/finding.py` (extended)
JSON, versioned, source of truth. Fields (superset of v1.1):
component/location, request/response refs, identity/role/tenant, technical &
plain descriptions, reproduction steps, oracle, impact demonstrated vs projected,
exploitability, blast radius, root cause, remediation, detection/telemetry, CVSS
vector, CWE/CAPEC/OWASP/ATT&CK, `requires`/`grants`, limitations, retest/regression
state. Reports (`reporting/`) become renderings of this JSON.

### 2.5 Attack graph integration — `offensia/core/attack_graph.py`
- Fed by the finding lifecycle (a validated finding emits nodes/edges).
- Nodes = capabilities/primitives; edges = `requires → grants` with evidence,
  confidence, preconditions, validation status.
- `paths()` returns **confirmed paths using only validated edges**; candidate paths
  (with unvalidated edges) are returned separately and clearly labeled.
- Recompute reachable paths on each new finding; rank by reachability, privilege
  gain, confidence, asset criticality, data sensitivity; support explicit crown
  jewels; identify the fix that breaks the most paths.
- MCP: `offensia_graph_paths(assessment, src?, dst?)`.

### 2.6 Planner / autonomous runner — `offensia/core/planner.py`
Drives the loop. Maintains (in state/ledgers): asset/surface ledger, assumption
ledger, hypothesis portfolio, experiment queue, priorities/dependencies,
identities/roles/tenants, coverage gaps, leads/anomalies, next-step + reason,
budgets (requests/time/turns/cost), negative results + revalidation conditions.

Per turn: read state → ask the LLM (via provider) for the next typed job **or**
derive one from the intelligence registry/doctrine → enqueue exactly one → execute
serially → oracle → persist → update graph/coverage → check stop conditions.

Controls: budget caps (requests/turns/cost/time) with hard stop; capability
registry **in the real flow** (`planner → registry → policy → adapter → executor →
normalizer → oracle → evidence → ledger`).

### 2.7 Provider in the loop — `offensia/providers/`
The runner calls Kimi/GLM for real (litellm-style), requiring `OFFENSIA_MODEL_ID`
+ API key. Offensive methodology stays out of provider code. Missing config is
surfaced (as today), and the runner refuses to start without a usable provider.

## 3. Safety model (v1.2)

- **Scope is law, per job.** Default-deny; every target validated before execution;
  denials recorded. This is the security boundary and is unchanged.
- **No generic command.** Only validated `ExecutionJob`s run.
- **Human safety gate — lateral movement only.** A job whose `risk_class` is
  `lateral_movement` pauses for explicit human confirmation before executing. All
  other high-impact classes (RCE, persistence, credential replay, MFA bypass,
  domain-controller actions, certificate issuance) execute without a pause, but are
  flagged and recorded in the ledger with their `risk_class`, and doctrine still
  directs the least-impact proof. (Operator's deliberate choice for authorized
  engagements; the gate is prudence, not the boundary.)
- **Non-disruptive — no availability impact (code-enforced).** OffensIA never runs
  an action whose effect is to degrade or deny service. Any job classified as
  availability-affecting — DoS/flood, stress/load, resource exhaustion, or a
  known crash/hang-inducing exploit — is **refused, not executed** (policy blocks
  `risk_class in {dos, availability_impact, crash}` and any tool/argv on the
  disruptive denylist). Before and during a job the executor probes target health;
  if the target is already unavailable, or a job would push it toward
  unavailability, execution **halts** rather than continuing. Findings for such
  classes may be reported as HYPOTHESIS from safe indicators, never proven by
  actually causing an outage.
- **No destruction of target-owned data (code-enforced).** OffensIA never deletes,
  overwrites, truncates, or otherwise destroys any file, object, table, or record on
  the target that it did not itself create during the engagement. The executor
  tracks the provenance of every artifact it writes to the target (marked
  `origin=offensia`, with the engagement id); **cleanup removes only those
  self-created artifacts.** Any job whose effect would modify or delete a
  pre-existing target-owned resource is refused. Where a test class normally implies
  a destructive action, OffensIA proves it with an inert, self-created canary and
  removes only that canary.
- **Budget** caps stop runaway loops. **Serial execution + hash-chained ledger +
  resume** preserve causality and prevent lost/duplicated work. **Target content
  stays UNTRUSTED** and never becomes an instruction.

## 4. Interfaces summary (MCP + CLI)

MCP tools: `offensia_run_job`, `offensia_finding_get`, `offensia_graph_paths`,
plus existing `offensia_scope_*`, `offensia_recon_crawl`, `offensia_coverage_*`,
`offensia_ledger_verify`, `offensia_report_generate`. Removed: `offensia_exec`.

CLI: `offensia run <assessment> --objective "..." [--max-budget N] [--max-turns N]`
and `offensia resume <assessment>` (deterministic resume from checkpoint).

## 5. Decomposition into implementation plans (sequenced)

Each plan produces working, tested software on its own.

1. **Execution backbone** — `jobs.py` (typed jobs + validation), capability registry
   in-flow, `executor.py` (serial, lock, actions.jsonl, streaming, atomic
   checkpoint, resume). Remove `offensia_exec`; add `offensia_run_job`.
2. **Semantic validation** — oracle framework + the four oracles + canonical finding
   model + oracle-driven promotion (stricter EXPLOITABLE/CONFIRMED_IMPACT).
3. **Attack graph integration** — findings feed the graph; validated-only confirmed
   paths; ranking; `offensia_graph_paths`.
4. **Autonomous planner/runner** — provider-in-loop, hypothesis/experiment queue,
   budgets, stop conditions, lateral-movement safety gate; `offensia run`/`resume`.

## 6. Testing strategy

- **jobs**: scope validation per target, argv allowlist, cap enforcement, refusal on
  out-of-scope / unknown tool; **availability guard** refuses dos/crash/stress jobs
  and disruptive-denylist argv; **destruction guard** refuses delete/overwrite of a
  pre-existing target resource while allowing a self-created canary.
- **executor availability**: a job is halted (not retried in a loop) when the target
  health probe fails before/after execution; cleanup removes only `origin=offensia`
  artifacts and leaves pre-existing data untouched.
- **executor**: single-active lock; actions.jsonl monotonicity; atomic checkpoint
  (temp+fsync+rename) survives a simulated crash mid-write; resume marks a
  no-terminal action `interrupted` and continues from the last confirmed one; stream
  files written incrementally.
- **oracles**: each oracle confirms only with baseline + negative control +
  reproduction; a WAF/block-page or timeout does not confirm; HTTP 200 without the
  expected object does not confirm; injected runner used for determinism.
- **finding**: canonical JSON round-trip; stricter promotion for EXPLOITABLE/
  CONFIRMED_IMPACT.
- **attack graph**: confirmed paths exclude unvalidated edges; recompute on new
  finding; ranking order.
- **planner**: with a mocked provider, one experiment active at a time; budget hard
  stop; lateral-movement job pauses (gate) while others proceed; resume after
  simulated interruption.
- All tests run without a live external target (mocked engines/provider).

## 7. Open items to confirm before/at implementation

- OOB listener for `OASTOracle`: local callback service vs external interaction
  server (impacts SSRF/blind-RCE confirmation). Ship `OASTOracle` interface in
  plan 2; wire a concrete listener when chosen.
- Provider call transport (litellm dependency vs a thin OpenAI-compatible client for
  Kimi/GLM endpoints); exact model ids remain configurable, never invented.
- Argv allowlist source per `tool_id` (static schema in repo vs derived) — start
  static.
- Budget accounting granularity (per-request vs per-turn cost) for `--max-budget`.
